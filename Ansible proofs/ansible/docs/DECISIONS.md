# Design decisions

Each entry records what was decided, why, and what it costs. IDs are referenced from code comments.

| ID | Decision | Reason | Trade-off / limitation |
|----|----------|--------|------------------------|
| D-01 | Ansible control node = **WSL2 Ubuntu 24.04** on the Windows 11 laptop, Ansible in a Python venv (`~/.venvs/ansible`) | Ansible does not run as a control node on native Windows. WSL is lighter than a separate control VM. A venv pins tool versions (`requirements-dev.txt`). The node is built by `control-node/setup_control_node.sh`, so it is reproducible from the repo. | Control node is a laptop, not a shared server; in production it would be a dedicated jump host or CI runner. |
| D-02 | Project lives in the shared team repo under `Ansible proofs/ansible/` | Follows the team's `<topic> proofs/` folder convention. | Path contains a space; commands must quote it. |
| D-03 | Repo is cloned on the Windows drive (`C:\Users\yassi\Com-615-group-respository`) and WSL mounts it with the `metadata` option (`/etc/wsl.conf`) | Without `metadata`, WSL shows Windows folders as world-writable (777) and Ansible **ignores `ansible.cfg` in world-writable directories** for security. With it, the folder is 755 and `ansible --version` reports the project config. One clone is usable from Windows (git, VS Code, Vagrant) and WSL (Ansible). | File access from WSL to the Windows drive is slow (see EXP-03). |
| D-04 | Collections installed to `~/.ansible/collections` (Linux filesystem), pinned in `requirements.yml` | Install into the repo on the Windows drive took >887 s and was not finished; native install took 46 s (EXP-03). Pinning makes module behaviour identical for every team member. | Each control node must run `ansible-galaxy collection install -r requirements.yml` once. |
| D-05 | Linux targets = **2 Ubuntu 24.04 Vagrant VMs** (VirtualBox), `srv-main-01` 192.168.56.21 and `srv-acq-01` 192.168.56.22 | Real systemd/sshd, so hardening and idempotency results are realistic (containers lack these). Two hosts = "multiple systems" across both sites at minimum cost. Linked clones, 1 vCPU / 1 GB each. | Stand-ins for NEL's ~20 servers. |
| D-06 | **PXE handoff contract** (assumption, confirmed with Jack that his Windows Server 2012 machine is only the PXE server): a freshly built server is Ubuntu 24.04, has a static IP in the lab range, a user `ansible` with passwordless sudo, and the control node public key in `authorized_keys`. Vagrant's provisioner (`lab/Vagrantfile`) reproduces exactly this state and nothing more. | Defines a clear boundary: PXE delivers a reachable OS, Ansible does all configuration. | The real values (IP range, user name) must be checked against Jack's final PXE build. |
| D-07 | Network target = **Cisco CSR1000v (IOS XE)** at 192.168.56.10, `admin` account (privilege 15) | Same image, address and account as Ester's RESTCONF lab, so Manual CLI vs RESTCONF vs Ansible is compared on identical devices. | **Pending:** image not yet imported on this laptop (needs NetAcad download or export from Ester). DevNet always-on sandbox was tried as an alternative (EXP-01). |
| D-08 | `switches` group exists in the inventory but is **empty** | No Cisco IOS switch image runs in this VirtualBox lab. The group (and its variables) shows how NEL's 14 switches would be managed; adding one is one inventory line. `cisco.ios` modules are the same on Catalyst switches. | Switch-specific features (VLAN trunks, port security) are not demonstrated on real hardware. |
| D-09 | Inventory groups by **function** (`linux_servers`, `ios_devices` → `routers`/`switches`) **and by location** (`site_main`, `site_acquired`) | Configuration is decided by function; site groups let one inventory target or report on the acquired company separately. | A host appears in more than one group; variable precedence must be kept simple (site groups currently hold no variables). |
| D-10 | Vault layout: `group_vars/all/vars.yml` (plain) + `group_vars/all/vault.yml` (encrypted, `vault_` prefix). Vault password file at `~/.ansible/nel_vault_pass` (mode 600), outside the repo | A file named `group_vars/vault.yml` would be read as variables for a group called "vault". The `all/` directory form is the standard pattern, and the `vault_` prefix shows where every secret comes from. The repo is **public**, so the password file must never be inside it. | The vault password must be backed up and shared with teammates out-of-band. |
| D-11 | SSH host keys checked with **trust-on-first-use** (`StrictHostKeyChecking=accept-new`; `ansible_host_key_auto_add` for IOS) | Freshly PXE-built hosts have unknown keys; fully disabling checking would hide man-in-the-middle or a rebuilt host. `accept-new` trusts once, then rejects a changed key. | First connection is still trusted blindly. |
| D-12 | `.gitattributes` forces LF line endings in the Ansible folder | Windows Git has `core.autocrlf=true`; CRLF YAML fails yamllint on Linux. | None. |
| D-13 | Run logging: `log_path = evidence/logs/ansible.log` plus `profile_tasks` and `timer` callbacks | Every run leaves an audit trail and per-task timings for the comparison with manual CLI and RESTCONF. | Log grows over time; it is plain text in a public repo, so tasks handling secrets must use `no_log: true`. |
